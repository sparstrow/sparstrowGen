## Why

`doc/research/Sparstrowgen Agent Definition Library.md` is a research report
proposing a full 12-agent roster, 17 skills, and a `.sparstrowgen/blueprint.yaml`
stack-parameterization file, all built around a workflow (spec-kit specs/plans/tasks,
worktree-per-task, `.sparstrowgen/handoffs/`) this repo doesn't actually run.
`AGENTS.md` documents the real workflow instead: feature branches squash-merged into
`development`, promoted through `staging` to `main`, governed by the `doc/`
plans→tasks→code lifecycle.

The owner chose to build the automation-workflow *foundations* now and defer the
12-agent roster to a later phase, with three explicit decisions:

1. **Blueprint** is a `.sparstrowgen/blueprint.yaml` extracting the stack/commands
   already locked in `AGENTS.md` into one machine-readable file — not the research
   doc's generic, stack-agnostic schema (no invented `policy_profile` or fields this
   repo doesn't have). Prose in `AGENTS.md` §1 stays the human-readable source; the
   YAML is what future automation reads instead of restating stack facts inline.
2. **Workflow to build for** is the current `AGENTS.md` process, not the research
   doc's spec-kit/worktree-per-task assumption.
3. **MCP servers** to add beyond the existing `supabase`: `context7`, `shadcn`,
   `github`, `playwright`.

## What was built

- **`.sparstrowgen/blueprint.yaml`** — stack + commands mirror of `AGENTS.md` §1.
- **`.mcp.json`** — added `context7` (hosted HTTP, no auth), `playwright` (`npx
  @playwright/mcp@latest`), `github` (hosted HTTP at
  `https://api.githubcopilot.com/mcp/`, OAuth via `/mcp` — same pattern as the
  existing `supabase` entry, no token ever stored in the file), and `shadcn`
  (generated by the shadcn CLI's own `mcp init`, not hand-written).
- **`.claude/skills/shadcn/`** and **`.claude/skills/migrate-radix-to-base/`** —
  vendored via `npx skills add shadcn/ui --agent claude-code` (official source,
  tracked in `skills-lock.json` for drift detection, same mechanism already used for
  the existing `.agents/skills/supabase*` skills). `migrate-radix-to-base` came
  bundled from the same source repo; its trigger is narrowly scoped to explicit
  Radix→Base migration requests, so it sits idle and costs nothing until asked for.
- **`.claude/skills/worktree-orchestration/`** — authored from scratch, grounded in
  this repo's actual worktree mechanics (`EnterWorktree`/`ExitWorktree`, the
  port/data-dir isolation pattern in `.claude/launch.json` +
  `scripts/dev-preview.mjs`) and the `AGENTS.md` §2 branch/PR/cleanup rules — not the
  research doc's version of this skill, which assumes spec-kit.
- **`AGENTS.md` §1** updated: the MCP server list now matches `.mcp.json` (5 servers,
  each with why it's there), plus two accuracy fixes found in passing — the
  `packages/daemon/` line was contradicting itself against §4 (now marked as a
  planned split, not an existing package), and the "Vector Search: Supabase
  `pgvector`" line was flatly wrong (already corrected elsewhere in §4 — it's local
  `sqlite-vec`, cloud `memory_notes` has no vector column).

## Deferred

The research doc's 12-agent roster (`coordinator`, `architect`, `frontend-builder`,
etc.) and the 13 skills tied to it (`writing-handoff-manifests`,
`authoring-spec-kit-specs`, per-agent skills) are **not built**. They're designed
around a spec-kit/handoff-manifest workflow this repo doesn't run, and the owner
explicitly sequenced agents after this foundational tooling. Revisit
`doc/research/Sparstrowgen Agent Definition Library.md` Part B/C when that phase
starts — reconcile its proposed `.claude/agents/*.md` frontmatter and handoff schema
against whatever `blueprint.yaml`/skills look like by then, rather than building from
the doc verbatim.
