## TL;DR

While locking the small Teams feature (group agents + assign to projects), the founder described a
much larger vision: a **visual, agent-assisted multi-agent automation builder** living inside the
team. This doc captures that vision faithfully so it is not lost, maps it against what Sparstrowgen
already has, and names the one decision that must come first. It is **not** approved for build. The
small Teams wedge ships first (Pass 2); this gets its own design session.

## The vision (founder's words, organized)

When you open a team, you should be able to:

1. **Create tasks manually and assign agents.** Per task: assign one *or more* agents; configure
   **scheduled execution** (cron); set up **event-based triggers** that auto-run agents against the
   task; **save the task as a reusable template**.
2. **Deploy team task-templates to projects** — pick predefined tasks and apply them to a project.
3. **Create tasks conversationally** via a **Team Manager Agent** that sits at the top of the agent
   hierarchy and knows every agent's capabilities, skills, prompts, and responsibilities. It should:
   - Analyze a task request and decide if the existing agents can do it.
   - Recommend the most suitable agents; give **honest feedback** when the team lacks the capability.
   - Suggest improvements to existing agents (prompt/skill additions) **only when it won't disrupt
     their other assigned tasks**.
   - Recommend creating new agents / subagents when needed.
   - Propose an optimal task-execution workflow.
4. **Design workflows visually** — an n8n / Microsoft Power Automate-style **drag-and-drop canvas**
   where tasks, agents, triggers, conditions, tools, and actions connect into multi-agent execution
   pipelines. Low-code; buildable by the founder and by the Manager Agent together.

## The core insight — this is a convergence, not a new island

What's described is the **merger of four surfaces Sparstrowgen already has** into one builder:

| Vision piece | Already exists | Net-new to reach the vision |
|---|---|---|
| Tasks + assign agents | **Tasks** (`task.ts`): project, status, `assignedAgentId`, priority, spawns a run | multi-agent assignment; `teamId`; task templates |
| Scheduled execution | **Cron** (`cron.ts`): cronExpr → agent or pipeline, per project | link cron → a task |
| Multi-step workflows | **Pipelines** (`pipeline.ts`): ordered steps, `{{input}}`/`{{steps.N.output}}` piping, onFailure | branches, conditions, triggers, **visual editor** |
| Agent recommendation | **Agent Creator F3**: conversational build + FIND by capability | task-fit analysis, gap feedback, the Manager Agent advisor |
| Agent→agent delegation | **Messages** (`task.ts`): agent inbox, spawns runs | a manager orchestrating over it |
| Event triggers | partial (`trigger` field on pipeline runs) | real event-trigger engine |
| Visual designer | — | the canvas (biggest single piece) |

The execution substrate (runs, single-agent tasks, linear pipelines, cron, messages) largely exists.
The big net-new work is: the **visual graph editor**, a **richer execution model** (multi-agent +
conditions + triggers + actions vs today's linear pipeline), the **Team Manager Agent advisor**, and
**templates + deploy-to-project**.

## The first design question (before any build)

**Surface ownership.** This overlaps the existing Tasks, Pipelines, and Schedule pages. Building a
task list and a workflow canvas *inside* the Teams page would create duplicate surfaces (two task
lists, two workflow builders). So the first question is not "how do we build it" but:

> Do Tasks / Pipelines / Schedule get **absorbed** into the Team Workspace, **kept** as separate
> pages that the workspace links to, or **refactored** so one execution model backs all of them?

This decision shapes everything downstream and must be made in the dedicated session.

## Premises to challenge in the dedicated session

1. The visual builder is worth its cost **now** vs. extending the existing linear Pipelines with
   triggers + multi-agent (a far smaller step that reuses what's built).
2. The Team Manager Agent is a distinct product vs. an evolution of Agent Creator F3's FIND intent.
3. A team is the right *home* for tasks/workflows, vs. tasks/workflows being project-scoped with a
   team just being the cast of agents.
4. This should be built **before** a client app ships through the factory (see strategic flag).

## Strategic flag (founder's own recurring pattern)

The reframe plan (`Sparstrowgen-reframe-and-finish-plan.md`, Section "What I noticed") names this
exact pattern **four times**: generic ERP engine → agent harness → internal company app →
restructure-to-cloud. This automation builder is the **fifth** infrastructure idea arriving before
the first customer thing has shipped. The approved definition of "factory finished" is *the Seelin
website shipped through it*, not a workflow platform. This vision is real and worth building — but
the plan's standing guidance is to ship a real client job first, then build factory infrastructure
the job proved you needed. That is the founder's call to make in the dedicated session, with eyes open.

## Recommended decomposition (a graduation path, not a commitment)

If/when this is greenlit, the cheapest-first order that reuses existing surfaces:

1. **Multi-agent tasks + teamId** — extend `tasks` (one-or-more agents, `teamId`); show a task list
   in team detail. Reuses Tasks + the run engine.
2. **Cron-on-task + first event trigger** — let a task carry a schedule; add one real trigger type.
   Reuses Cron.
3. **Task templates + deploy-to-project** — save a task config; apply to a project.
4. **Team Manager Agent (advisor only)** — conversational "what should do this task" over the agent
   registry; recommendations + gap feedback. Grows from Agent Creator F3. No autonomous execution.
5. **Richer execution model** — branches/conditions/triggers on top of Pipelines (text/graph IR).
6. **Visual canvas** — the n8n-style editor as a view over that execution model. Last, because it is
   the most expensive and only pays off once the model under it is right.

This also resolves the deferred **agent template→instance** model (copy-on-deploy + per-project
`agent:self` isolation) — instances get created at step 1/2 when tasks actually run.
