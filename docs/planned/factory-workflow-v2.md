## Problem statement

Building Sparstrowgen has taken a month when the owner believes it should have taken a
week. The bottleneck is **not** compute or model access — the owner has two Claude accounts
(top-tier Fable), an `agy` (Antigravity) account, and heavy session budget. The bottleneck is
the **build process itself**:

1. **Two contradictory rulebooks, no arbitration.** `AGENTS.md` defines a gated contract
   (plan elsewhere → build an APPROVED `SPEC.md` → PR → human merge) for "other" harnesses,
   while explicitly exempting Claude Code, which plans *and* builds in one conversation with
   no gate. Nothing tells any agent which mode it is in. Result: work ships ungated — e.g. the
   0004 desktop installer merged with the packaged app completely non-functional, caught only
   by an after-the-fact manual boot test that is part of neither documented process.
2. **Idle capacity.** All that model access runs through one sequential thread. No parallelism.
3. **No verification gate.** `pnpm typecheck && pnpm test` green is treated as "done," but it
   never proves a shippable artifact actually works (the installer built green and didn't run;
   the Antigravity chat integration returns canned replies and was never caught).
4. **Doc procedure wastes tokens/time.** `APP.md` and the engine `ENGINEERING_PLAN.md` describe
   finished work but are still on the agent read-path as "source of truth," re-read and
   re-updated every session.
5. **Frontend was deferred on purpose** ("features first, minimal UI"). The owner now wants
   frontend, backend, and features all held to top-level quality — no more deferral.

## Premises (agreed in session)

- **P1 — one gate for every agent.** Claude Code and `agy` follow the *same* instructions and
  the *same* gate. No conversational-mode exemption.
- **P2 — one workflow, not three.** Collapse the page-by-page FACTORY-LOOP, the whole-engine
  master-plan track, and the ad-hoc plan-mode+intake track into a single loop, sized by scope.
- **P3 — verification is part of the gate.** Green typecheck+test is necessary, not sufficient;
  the agent must exercise the real artifact/feature and fix it before it counts as done.
- **P4 (risk, baked in) — parallelism needs file/module partitioning.** Phases that run in
  parallel worktrees must own non-overlapping files, or staging becomes merge hell.
- **P5 (risk, baked in) — auto-merge to staging is only safe gate-first.** Each agent branch
  must pass the full gate *before* it merges to staging, or the owner's review job gets harder.

## Git flow — staging as the agents' trunk

Today: every change is a PR the owner opens and merges by hand. That serial human merge is a
bottleneck.

**v2:**
- **`staging`** is the agents' integration branch. Agents branch off `staging`, build, pass the
  gate, and **auto-merge back to `staging`**. No human in this loop.
- **`main`** is the owner's release gate. The owner reviews accumulated work on `staging`, then
  opens **one** PR `staging` → `main` and approves it. That is the only human merge.
- Branch protection moves accordingly: `main` still protected (owner approval + checks); `staging`
  allows agent auto-merge but **only via the gate** (required status checks: typecheck, test,
  usability, author-check).
- CI/CD releases fire on `main` (tagged), so the packaged always-on app only ever updates from
  owner-approved code.

**Open decision D-A (below):** does `staging` require a green gate as a *branch protection rule*
(GitHub enforces it), or is the gate enforced by the agent's own workflow before it merges?

### Git decisions (locked 2026-07-14)

- **Merge strategy: squash, always** — at both levels (agent branch → `staging`, and `staging` →
  `main`). Agent working commits are disposable scaffolding; `main` reads as one clean commit per
  feature. Owner never reads diffs.
- **Branch cleanup is automatic.** Remote side: GitHub "Automatically delete head branches" is
  **enabled** (source branch removed on merge). Local side: `fetch.prune = true` (repo-local, set)
  auto-clears dead remote-tracking refs, and **agents delete local branches whose upstream is
  `[gone]`** as a workflow rule. Squash-merge means `git branch -d` can't detect merges — the
  `[gone]` marker is the safe signal; never delete a branch checked out in another worktree.
- **Release model: staging branch (chosen over tag-gated trunk).** Fits parallel agents + an
  always-on packaged app: `main` stays release-quality so the stable app never updates from
  unseen code; `staging` is the integration/dogfood area. **The owner reviews the running product
  on `staging`, not code diffs** — code correctness is already caught by the per-branch
  verification gate. Promotion `staging` → `main` is the single human gate; CI ships on `main` tags.

### UAT / preview mechanism (locked 2026-07-15)

"Review the running product on `staging`" needs a concrete *how* — a git branch is not a running
environment, and this is a local desktop app with no shared staging URL. Two fidelity levels
exist; only the second catches packaging-class bugs (the 0004 installer bug lived *only* in the
packaged artifact, invisible in dev — proof that dev-build UAT can ship a broken package).

- **Now (locked):** UAT = run the `staging` **dev build on the dev port (48751)**, separate from
  the always-on stable app on 48750. **This makes intake 0005 (dev/prod port split) a hard
  dependency of the UAT step, not optional.** Good for behavior/UX testing; does not exercise the
  packaged artifact.
- **Deferred (the "best" end state, graduate on demand):** a **beta release channel** — CI builds
  a packaged beta from `staging`, and a separate "Sparstrowgen Beta" install notify-updates from
  it exactly as the stable app updates from `main`, so UAT tests the real packaged artifact.
  Reuses 0004's electron-updater machinery (channels). Not built now — reach for it when
  packaging-fidelity actually bites, per the no-speculative-future-proofing bar. Logged in
  `DEFERRED_SCOPE.md`.

## Parallelism across worktrees

The planning step must output phases annotated for parallel execution:

- Each parallel phase declares the **files/modules it owns**. Two phases may run concurrently
  only if their ownership sets are disjoint (P4).
- The owner (or a routine) assigns each parallel phase to a worktree on a specific agent
  account: e.g. Claude-A → phase 2, Claude-B → phase 3, `agy` → phase 4.
- Each worktree branches off `staging`, builds its phase, gates, auto-merges to `staging`.
- Serial phases (shared-file, or dependency-ordered) run one at a time.

The plan is the coordination artifact — it is what makes "3 accounts building at once" safe
instead of a merge pileup.

## The verification gate — "Definition of Done" (the missing piece)

A phase is **not done** until all of the following are green on its branch. This is the same bar
whether Claude Code or `agy` built it, and it is the standard Sparstrowgen's own agents will hold
the apps *they* build to.

1. **Typecheck** — `pnpm typecheck`, 6/6.
2. **Unit + integration tests** — `pnpm test`, plus new tests for the feature/fix built (a bug
   fix ships with a regression test; a new surface ships with coverage of its golden path).
3. **Real-artifact usability test** — the agent drives the actual running thing, not a mock:
   - UI/backend change → boot the dev server (or packaged app) and exercise the flow in a real
     browser (cloud preview / the in-app Chrome / Antigravity's browser), observe it work.
   - CLI/integration change (e.g. Antigravity chat) → actually send a real message and read the
     real reply; a canned/echo response is a FAIL.
   - Packaging/artifact change → build and boot the artifact (the boot test that caught the
     0004 installer bug becomes a required step, not luck).
   - If it's broken, the agent fixes it and re-verifies before the phase counts as done.
4. **Design/UI bar** — frontend is now top-level (see below): the surface must match the design
   system (spacing, hierarchy, states: empty/loading/error), not just render.

> This standard is dual-purpose: it governs building Sparstrowgen now, and it becomes the
> testing contract Sparstrowgen's agents apply to the production apps they build.
