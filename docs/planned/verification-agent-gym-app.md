# Plan: Outside verification agent + persistent Team for the gym-app test project

## Problem Statement

Intake [0006](../intake/0006-live-test-project-gym-app-verification-target-2026-07-14.md) asks
for one permanent, standing live test project (the Muscle-Specific Gym App) built with real
agents and pipelines, that every future Sparstrowgen feature gets verified against. Curator's
mode/routing check on 0006 surfaced a real fork: is the deliverable (A) a one-time bootstrap
action using already-built features, or (B) new software? Talking it through revealed it's
neither exactly — the missing piece is *who does the bootstrapping and how the work stays
alive afterward*, which this office-hours session resolves.

## Premises (confirmed 2026-07-15)

- P1 (refined during dialogue): an **outside agent** — not an in-app system agent calling
  backend APIs — drives Sparstrowgen's actual UI like a real user (Agents, Teams, Pipelines,
  Task Board, Memory, Schedule), reusing the existing P10 Team Workspace (Teams, `team-manager`
  system agent, team-scoped pipelines) rather than inventing new agent-coordination
  infrastructure. This doubles as continuous UI/UX validation of Sparstrowgen itself. **Agreed**
  (refined from the original P1).
- P2: blocker/feature-change reports from the verification work reuse the existing Listener
  capture format — a real intake doc in this repo's `docs/intake/` — which requires the
  gym-app project to be set up with write access back to this repo (registered as a project
  pointing at this checkout, not an isolated external repo with no path back). **Agreed**.
- P3: "production-grade" is scoped, not the full enterprise SaaS release lifecycle. What
  applies: dev-complete (features work, no unfinished code, tests written, reviewed), QA
  (functional/regression/cross-browser/accessibility **+ explicitly named security review and
  performance testing**, both new relative to CLAUDE.md's current Definition of Done), staged
  (the existing `staging` branch model), and release-noted (a "what changed" note per shipped
  feature — also new, and ties directly into the release-notes generation already built for
  intake 0004). What's explicitly **out of scope**: blue-green/canary/rolling deployment,
  feature-flag gradual rollout, SSL certificate rotation, customer success briefings, marketing
  announcements — all assume a multi-tenant SaaS with real paying users; this is one local app
  on one machine. **Agreed** (after the user supplied the full generic checklist and we scoped
  it down together).

## Approaches Considered

**A — Minimal:** one outside agent (Claude Code/agy + browser-driving tools), one-shot,
manually triggered each time. Effort S, risk low. Reuses 100% existing capability. Weakness: no
persistent state between runs, one agent wears every hat.

**B — Ideal (chosen):** the outside agent's job is bootstrap-only — create the project, Team,
test agents, and a team-manager-coordinated pipeline through the real UI, once. Ongoing feature
work then runs through the in-app `team-manager` agent and the team's pipeline, re-triggered by
Sparstrowgen's existing Scheduler (cron). The outside agent's role becomes periodic supervision:
check progress, and when the team is genuinely stuck, write the blocker back as a real intake
doc. Effort M, risk medium (real integration across Team Workspace + Scheduler, may surface
genuine P10 bugs). Reuses the most existing infrastructure and is naturally permanent/recurring,
matching 0006's own requirement without relying on the owner remembering to re-trigger it.

**C — Lateral:** skip the in-app-agents-build-it question; the gym app gets built
conversationally, the same way Sparstrowgen itself has been built. Effort S/M, risk low, but
dodges the actual question 0006 asked (can the factory's *own* agents build a production app).

**Recommendation: B**, with A as its natural first step (bootstrap-only is literally B's phase
one) — the only approach that answers what was actually asked.

## Implementation Tasks

### Phase 1 — Bootstrap (outside agent, one-shot)
0. **Where the gym app's code lives, precisely:** its own separate checkout/repo — the
   registered Sparstrowgen project's `rootDir` points at *that* checkout, not at this
   Sparstrowgen repo. The gym app's generated source code never enters this repo. Only intake
   docs (blocker/feature-change reports) get written back here, over a *separate* path: the
   automated capture step authenticates as the existing machine-user identity from the
   git-automation design (the same PAT/profile already used for agent→GitHub operations, not a
   new credential), so it can push a branch + open a PR against this repo specifically for the
   capture doc — distinct from whatever access the gym-app project's own agents have to their
   own separate checkout.
0.5. **Authentication:** the outside agent's browser session needs the per-install bearer
   token (`config.apiToken`, injected into the served UI's `index.html` — see
   `packages/core/src/api/server.ts`) before it can drive any authenticated page. Bootstrap step:
   read the token from the running instance (env var, or the injected page value) and carry it
   through the agent's browser session — same mechanism the UI itself already relies on, not a
   new auth path.
1. Launch an outside agent (a Claude Code session with Browser-pane tooling, pointed at the
   running packaged Sparstrowgen app or dev server) with an explicit task list:
   - Projects → create "Muscle-Specific Gym App" (registered so its rootDir/checkout can
     receive intake docs back into *this* repo — see P2).
   - Teams → create a team for it (e.g. "Gym App Builders").
   - Agents → create the test agents assigned to that team (at minimum a builder-role agent
     and a reviewer/QA-role agent).
   - Pipelines → create a team-scoped pipeline via the `team-manager` draft-pipeline flow,
     targeting the gym app's feature list (from 0006: workout routines, weight/reps tracking,
     exercise guidelines, before/after photos, gym reminders, diet/nutrition, exercise
     analysis, AI chatbox, calisthenics learning, dashboard/sleep analysis).
   - Exercise every other nav surface at least once during setup (Task Board, Memory, Schedule,
     Terminals, Messages) — this is what naturally catches UI bugs like 0008/0009.
   - Any blocker hit during bootstrap → write a real intake doc, following the **git write path**
     below (never a direct commit to `main`/`staging`).
2. Write the gym app's own scoped Definition of Done (per P3 above) as a doc inside the gym-app
   project once it exists.

**Git write path for automated intake capture (both phases):** an automated process writing to
this repo follows the same rule as any other agent output — a dedicated branch (e.g.
`agent/gym-app-capture-<date>`), pushed, PR opened for the owner to review. Never a direct
commit to `main` or `staging`, and never auto-merged — a capture isn't "in progress" until a
human (or the Curator, per the normal flow) has actually looked at it, same as every other
intake doc.

### Phase 2 — Recurring (Scheduler + Team, mostly unattended) — gated on a Phase 1 retro, not automatic

**Safety requirements, non-negotiable before Phase 2 goes live** (an unattended daily cron
driving autonomous agent runs is the single biggest operational risk in this plan otherwise):
- **Failure cap / kill switch.** A consecutive-failure threshold on the team's pipeline (e.g. 3
  failed runs in a row) auto-pauses the schedule — never burns runs against the same wall for
  days waiting on a manual check-in. Surface the pause on the Task Board / a notification so it
  isn't silent.
- **Cost/time budget.** An explicit ceiling on run count or wall-clock time per cadence window,
  consistent with the existing global-concurrency and per-run-timeout mechanisms core already
  has — not a new unbounded loop.
- **Write-scope check.** EH7 (untrusted-run memory WRITE clamp) is a known-open gap — confirm
  what write scope a scheduled team run actually gets *before* turning this on nightly, not
  after. If the clamp isn't in place, scope these runs as untrusted/sandboxed until it is.

3. Configure Sparstrowgen's existing cron Scheduler to re-trigger the team's pipeline on a
   cadence (e.g. daily), with the failure cap and budget above wired in from the start.
4. **Outside-agent supervision is manual/on-demand, not itself scheduled** (owner-triggered when
   they want a check, not a second cron job) — a deliberate human trigger point so the two
   schedules (in-app pipeline cron vs. outside-agent supervision) don't get conflated. Review the
   team's recent runs/Task Board state; if a task is stuck beyond the auto-pause threshold above,
   write the blocker as a real intake doc via the git write path above.

## Success Criteria

- The gym-app project, team, agents, and pipeline exist and are visible in Sparstrowgen's UI,
  created through the UI itself (not seeded via direct DB/API calls).
- At least one full pipeline run has produced real, working progress on a named gym-app feature.
- The capture path (blocker → branch → PR → this repo's `docs/intake/`) has been exercised
  end-to-end at least once — forced deliberately if no real blocker occurs during setup, so this
  isn't an unfalsifiable "if any occurs" check.
- The Scheduler is re-triggering the pipeline on its own, without manual intervention, per P1's
  "permanent" requirement, with the failure cap/kill switch verified to actually trip (also
  forced deliberately at least once, not just assumed to work).
