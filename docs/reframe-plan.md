## Approaches Considered

### Approach A: Ship-only (minimal)
Audit's 3-item finish list + remote access, then build Jameel. No readiness work.
- Effort: S (human ~1–2 days / CC ~1–2 hrs). Risk: Low now, Med later.
- Pro: fastest to a shipped customer app; zero premature work.
- Con: leaves the absolute-path landmine to retrofit later; "easy migration" stays a hope with no plan.

### Approach B: Migration-ready (CHOSEN)
Approach A plus three cheap decoupling moves and a written migration plan.
- Effort: M (human ~3–5 days / CC ~half a day). Risk: Low.
- Pro: delivers the "easy to migrate later" you asked for at low cost; the path fix also unlocks multi-machine sync; de-risks cloud on paper.
- Con: a few days with no customer-visible output; needs discipline to not creep into a real migration.

### Approach C: Abstract-now (heavy)
Proactively build storage/queue/remote-execution abstraction layers.
- Effort: L (human ~2–3 weeks / CC ~few days). Risk: High.
- Con: the trap in an engineering costume — you'd guess the abstractions wrong without real cloud pressure and rebuild anyway (your doc's "generic-engine trap"). Rejected.

**Sub-decision — DB:** stay on SQLite now (chosen) vs Postgres-now vs PGlite-now. Postgres-now looks like "one path" but secretly drags the memory-search rewrite (FTS5 + sqlite-vec → tsvector + pgvector) forward for an unproven tool, plus a server to run every dev session. Rejected. Switch happens at Supabase-migration time.

## Recommended Approach

**Approach B + SQLite-now.** Concretely, the work, in order:

**Tier 0 — Finish list + auth (do first):**
1. **Working directory fix.** (Corrected by autoplan Eng review: NOT ~5 lines.) Make a run use the project's `rootDir` as its cwd. The precedence (`rootDir` → `agent.cwd` → `tempDir`) lives in the providers, not `run-manager` alone: add `rootDir?` to the spawn options, resolve `project.rootDir` in `start()`, and use it in both providers (claude-code + gemini, headless + interactive). Keep `tempDir` — it is the MCP-config scratch dir, NOT interchangeable with cwd. Add an `fs.existsSync(rootDir)` guard so a bad path fails with a clear error, not an opaque spawn ENOENT. Realistic: ~half a day, ~6 files, + a test. OR zero-code interim: set a build agent's `cwd` to the target folder.
2. **AUTH (NEW — ship-blocker, before any remote access).** The REST API has no auth and `cors:{origin:true}` (`server.ts:32`, `:63-78`) while it spawns host processes — drive-by RCE today, internet-wide RCE if exposed. Add a server-wide `onRequest` bearer/shared-secret hook on `/api/*`, `/ws`, `/mcp`, and the static UI; lock CORS to the dashboard origin; treat `extraArgs`/`permissionMode`/`cwd` as privileged fields. ~half a day. (Recorded risk: `sparstrowgen-auth-gap`.)
3. **Backup.** `git init` the vault (`C:\Sparstrow\memory`) to a PRIVATE repo (confirm no secrets in memory notes first). Back up the SQLite DB using the consistent `data/backups/` snapshot or `sqlite3 .backup` — NEVER commit the live WAL `.db`; the daily auto-push must copy a clean snapshot (app idle), not the hot file. Daily auto-push via Task Scheduler. ~$0, one afternoon. The one durability item that must exist before a paying client.
4. **Verify the embedder.** Confirm the BGE model downloaded (memory page status). If not, you're in keyword-only mode, which is fine. 2 minutes.

**Tier 1 — Remote access (ONLY after Tier 0 auth exists):**
5. **Secure remote access** to the local instance. Prefer **Tailscale with ACLs** (private tailnet). If you use a **Cloudflare Tunnel, Cloudflare Access in front is mandatory** — a bare tunnel publishes the app to the whole internet, and "no open ports" is NOT access control. This is safe only because Tier 0 added auth; without it, remote access = publishing RCE. Gets you "monitor + command from any device" over the dashboard + WebSocket hub that already exist.
6. **Mobile-responsive pass** over the existing dashboard/run views so it's usable on a phone. Keep it bounded to *your* single instance: no accounts, no multi-tenant, no "customer environments."

**Tier 2 — Migration-readiness (revisit only after the first paid app ships):**
7. **Kill absolute paths in the DB.** (Corrected: NOT globally cheap — ~1 day.) The two DB columns `cwd` (`schema.ts:12`) and `root_dir` (`schema.ts:35`) are cheap, but `config.vaultPath` is read in 9+ sites across 7 files including the path-traversal SECURITY guard (`vault.ts:34`) and the agent prompt (`preamble.ts:41`). Existing rows hold absolute strings, so this needs a data-backfill migration (hand-written SQL). Re-test the traversal guard after the change.
8. **Quarantine the SQLite-only code.** FTS5/sqlite-vec are already confined to the memory module (`indexer.ts`, `search.ts`, `search-store.ts`) — good. Add a CI grep asserting no `fts5|vec0|getSqlite` outside `memory/` + `system.ts` to keep it enforced (note: `getSqlite()` raw handle currently leaks into `system.ts:37`).
9. **Execution seam (claim corrected).** `SpawnSpec` (`providers/types.ts`) abstracts only argv/env construction; execution is hardcoded local in `run-manager` (`spawn`, `readline` over stdout, `treeKill(pid)`, `sweepOrphans`). `ModelProvider` has NO execute method, so a remote-spawn provider is NOT additive as-is. To make remote additive you must invert the seam: add `start(spec, handlers): RunHandle` to the provider and move spawn/stream/cancel into a `LocalProcessRunner` (~1 day). Deferred — you chose to downgrade the claim, not do the refactor now.
10. **Write `MIGRATION.md`** (corrected outline below). De-risk the cloud move on paper.

**Optional small win:** bump `DEFAULT_GLOBAL_CONCURRENCY` (currently 4) to taste (e.g. 6–8) if real builds want it. Config change, not architecture.

## MIGRATION.md (outline to write in Tier 2, step 9)

Trigger conditions (do NOT migrate before one of these is true):
- A second machine in active simultaneous use, OR an always-on hosting need, OR paying multi-user load.

The move, when triggered (autoplan-corrected — this is multi-day, not "config + one rewrite"):
1. **DB schema:** SQLite → Supabase Postgres. Swap the Drizzle driver/dialect, but the schema is hand-written SQLite DDL (`migrations.ts`), so it needs a real DDL port: `INTEGER PRIMARY KEY AUTOINCREMENT`, `text({mode:'json'})` → `jsonb`, `integer({mode:'boolean'})` → `boolean`, datetime-as-TEXT. Not a verbatim driver swap.
2. **Sync → async (biggest hidden cost):** `better-sqlite3` is synchronous; node-postgres is async. Every `.get()/.run()/.all()` across `run-manager`, the routes, `agent-memory`, etc. becomes `await`. A repo-wide refactor, not config.
3. **Memory search:** FTS5 → Postgres `tsvector`/GIN (or `pg_trgm`); sqlite-vec → **pgvector** (Supabase-native). Rewrite confined to the memory module.
4. **Execution:** requires the RunHandle seam inversion from Tier 2 step 9 first; THEN add a remote-spawn provider. Not additive until that refactor exists.
5. **Backend:** Fastify → container on the chosen host. Frontend (React/Vite) → Vercel.
6. **Paths:** relative (from Tier 2 step 7), so nothing breaks across environments.
7. **Multi-tenancy / auth:** only if the factory ever serves more than you (it shouldn't — that belongs to Shelfree).
